    # ADR 0001: Disciplina de migraciones de schema en produccion

    **Estado:** Accepted
    **Fecha:** 2026-05-02
    **Contexto Phase:** 38

    ## Contexto

    Entre 2026-04-09 y 2026-05-01 acumulamos drift sistemico entre el sistema de tracking de migraciones de Drizzle (`drizzle.__drizzle_migrations` en prod + `_journal.json` local) y el estado real del schema en `erp_sanchez`. Las causas:

    1. **2026-04-09 (quick task `260409-jwl`)**: se generó `migration-prod.sql` con 16 CREATE TABLE faltantes pero NO se ejecutó contra prod en ese momento; quedó como Pending Action en el SUMMARY.
    2. **2026-04-28 (quick task `260428-mig`)**: 19 dias despues, se aplico `migration-prod.sql` via `psql -f` (16 CREATE TABLE + 2 ALTER + 39 CREATE INDEX en una transaccion). El `__drizzle_migrations` no quedo sincronizado con la realidad porque el SQL fue ejecutado fuera del lifecycle de drizzle-kit.
    3. **2026-04-29 (quick task `260429-rec`)**: se aplico `0003_add_columna_inv_articulos.sql` manualmente via psql para agregar la columna `inventarios_articulos.columna`. La entry de `0003` quedo ausente en `_journal.json`.
    4. **2026-05-01**: durante smoke playwright de Phase 29, `/propiedades` retorno 500 porque las tablas `prop_*` no existian en prod. Se aplicaron `0004_phase29_propiedades.sql` y `0005_phase29_cache_trigger.sql` manualmente via psql.

    Resultado: `_journal.json` desfasado (5 entries con la 0003 faltante), `drizzle.__drizzle_migrations` sin entries para varias migraciones aplicadas, riesgo concreto de que un futuro `pnpm db:migrate` o `pnpm db:push` re-ejecute SQL contra prod (con potencial corrupcion).

    Phase 38 reconcilio el tracking via journal + INSERT idempotente (D-01 a D-04). Este ADR codifica la convencion para evitar la repeticion.

    ## Decision

    **Cualquier cambio de schema en produccion va por `pnpm db:migrate`** ejecutado contra la DB de prod. Esto incluye:

    - CREATE TABLE / DROP TABLE
    - ALTER TABLE (add column, drop column, rename, change type)
    - CREATE INDEX / DROP INDEX
    - Cualquier DDL

    **Excepcion unica documentada**: emergencia donde aplicar la migration por el lifecycle de drizzle-kit es operativamente imposible (ej: prod down y necesitamos restorar inmediatamente). En ese caso:

    1. La emergencia se documenta como quick task con SUMMARY explicito.
    2. El SUMMARY lista Pending Actions cubriendo el sync posterior:
       - Generar migration formal (`pnpm db:generate`).
       - Aplicar el INSERT en `drizzle.__drizzle_migrations` con hash + timestamp correctos.
       - Actualizar `_journal.json` y commit.
    3. **Cada Pending Action que toque prod queda como `BLOCKING-PROD-*` todo en `.planning/todos/pending/`** hasta que se valide la ejecucion. Esto previene que las acciones queden latentes semanas (la causa de Phase 38).

    ## Consecuencias

    **Pros:**
    - Trazabilidad completa: el journal + `__drizzle_migrations` son la fuente de verdad del estado del schema.
    - `pnpm db:check` (CI) detecta drift antes del merge a main.
    - Healthcheck `/api/health/db` detecta drift al boot del container, no al primer uso (lo que costo 4 dias en abril 2026).
    - Devs nuevos no pueden hacer `psql` directo sin marcarlo como excepcion documentada.

    **Contras:**
    - Overhead en emergencias: hay que pasar por `db:generate` + commit + deploy en lugar de un `psql` rapido.
    - Mitigacion: la excepcion unica esta documentada en este mismo ADR; los SUMMARYs `260428-mig` y `260429-rec` son ejemplos legitimos del uso correcto de la excepcion.

    ## Alternativas consideradas

    - **psql directo en prod sin sync**: rechazado, es exactamente lo que causo Phase 38.
    - **`pnpm db:push` en prod**: rechazado, `db:push` es destructivo y no respeta el journal. Solo apto para DBs locales de dev.
    - **Bloqueo total de psql en prod via permisos**: rechazado, eliminaria la valvula de escape para emergencias reales.
    - **`drizzle-kit check` en pre-commit local**: rechazado por overhead local + no requiere DB local levantada (ver D-09 en CONTEXT.md de Phase 38). Solo CI.
    - **Logging mejorado del SQL error cause en backend**: aplazado (D-12). Es deteccion post-hoc, no prevencion.
