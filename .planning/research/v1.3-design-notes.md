## Decisiones cerradas

### Identificación de artículos

1. **SKU es el identificador universal** en líneas de comprobantes (orders, sales, purchases, existencias, inventarios_articulos). Reemplaza `codigo` como FK desde tablas hijas.
2. **`codigo` deja de ser PK** de `articulos`. Pasa a ser campo agrupador (NOT UNIQUE, indexado).
3. **`sku` es PK** de `articulos` desde el día 1.
4. **Sin variantes**: `sku = codigo` (misma cadena). Una sola fila por artículo.
5. **Con variantes**: N filas con mismo `codigo` y SKUs distintos compuestos como `codigo + slug_atrib1 + slug_atrib2 + …`.
6. **El SKU siempre lleva `codigo` adelante**. La receta concatena `codigo` + slugs de atributos según orden definido en el template. `codigo` no figura en la tabla `template_atributos` — es prefijo implícito.

### Modelo de artículo

7. **Single-table plano** — no hay separación "artículo madre" vs "variantes". Todas las filas viven en `articulos`.
8. **Datos comunes duplicados** entre filas con mismo `codigo`. Aceptado.
9. **Consistencia de datos comunes**: app-level. UI presenta dos formularios:
   - "Datos del modelo" → `UPDATE articulos SET … WHERE codigo = X`
   - "Datos de la variante" → `UPDATE articulos SET … WHERE sku = Y`
   DB no impone constraints de consistencia entre filas hermanas.
10. **"Tiene variantes" implícito**: un artículo tiene variantes si existe más de 1 fila con su `codigo`. No hay flag explícito.

### Variantes (cuando se activen)

11. **Atributos configurables N×M** — admin define qué atributos aplican por template. Cada atributo tiene un catálogo de valores con `(id, nombre, slug)`.
12. **Stock por SKU**: las existencias referencian `sku` (transparente para artículos sin variantes porque `sku = codigo`).
13. **Precio absoluto por variante** — cada fila guarda su propio `precio` final. No hay modificadores relativos del padre.
14. **NO JSONB para atributos** — se guardan como columnas estructuradas (FK a catálogos). Razón: simplicidad de queries, vista cruda elocuente, IA-friendly, performance.

### Templates (la "receta")

15. **Tablas en DB desde día 1** — `articulos_templates` + `template_atributos` con receta. UI de admin para editarlas.
16. **1 solo template default al inicio** (`nombre='default'`). Modelo soporta multi-template para extensibilidad futura.
17. El template define: qué atributos aplican, cuáles son variantes, cuáles entran al SKU + orden, cuáles entran al nombre + orden.
18. **Flag `nombre_auto`** por artículo. Si true, el nombre se regenera al guardar concatenando atributos del template según receta.

### Cambios de schema del template

19. **Preview + cascade + history**:
    - UI muestra preview de cuántos SKUs/nombres se afectan
    - Confirmación
    - Transacción atómica: `UPDATE articulos.sku` + cascade a tablas hijo (orders, sales, purchases, existencias, inventarios_articulos) vía mapping viejo→nuevo
    - `articulos.sku_anterior` (NULL) guarda el SKU previo (idempotencia)
    - Tabla `articulo_sku_history` append-only para audit y "deshacer último cambio masivo"
20. **`codigo_barras` separado del SKU** — el código de barras impreso en etiquetas físicas NO se regenera en cambios de schema.

### Stock redesign (de conversación previa, abr-2026)

21. **`columna` se renombra a `ubicacion`** en todas las tablas (`existencias`, `inventarios_articulos`). Palabra general — cubre columnas, estanterías, percheros, cajones, etc.
22. **Sectores transversales** — agrupan ubicaciones físicas del depósito; no son por inventario ni por existencia. Una `ubicacion` puede pertenecer a M sectores.
23. **Storage de relación sector↔ubicación**: tabla pivot `sector_ubicaciones` (no JSONB).

## Gray areas (defer a `/gsd-discuss-phase N`)

### Q1 — Modelo de columnas para atributos del rubro

Cuatro approaches presentados; no resuelto. Trade-off central: vista cruda elocuente vs. flexibilidad multi-rubro.

- **A1**: Pocas comunes en columnas + pivot `articulo_atributos` para extras del rubro
- **A2**: Slots genéricos numerados, mapeados por template
- **A3**: Una columna por tipo real, NULL para los que no aplican (wide)
- **A4**: Tabla por template (inheritance)

Sub-cuestiones del usuario aún sin resolver:
- La inconsistencia "fijas (marca, talle, color, material…) vs propAux1..5" — quiere unificarla
- Para automotor: `talle/color/material` están de más; faltan `aplicacion` y otras del rubro

### Q2 — Vincular atributos por ID, slug, o nombre

Trade-offs presentados. Recomendación tentativa: **slug + nombre denormalizado** (cache via trigger). NO confirmado por el usuario. El usuario expresó preocupación por:
- Browsing visual amigable (preferir nombre legible sobre id)
- IA-friendly (info elocuente a mano sin requerir joins)

### Q3 — Vehículos compatibles

Modelado tentativo como entidad relacional aparte (`vehiculos` + pivot `articulo_vehiculos`). No es un atributo. **No confirmado si entra a v1.3** o queda para milestone posterior. Trabajo grande por sí mismo (catálogo de vehículos, UI de fitment, posible import de fuentes externas tipo ACES).

### Q4 — Atributos finales del template default

Propuesta inicial mostrada al usuario:

| Tipo | Catálogo | Variante | En SKU | En Nombre |
|---|---|---|---|---|
| objeto | sí | no | no | 1 |
| calificador (¿renombre de `adjetivo`?) | sí | no | no | 2 |
| marca | sí | no | sí (1) | 3 |
| modelo | text libre | no | no | 4 |
| presentacion | sí | no | no | 5 |
| talle | sí | sí | sí (2) | — |
| color | sí | sí | sí (3) | — |
| material | sí | no | no | — |
| medida | text libre | no | no | — |

Usuario aclaró: "este modelo no lleva variantes, pero quiero que el modelo lo soporte". O sea, template default **flat sin variantes** hoy, pero la mecánica de variantes existe en el schema. **NO confirmado** qué atributos entran realmente al template default para automotor.

### Q5 — `propAux1..5` actuales

Cambio cosmético TS-only. **NO confirmado** si entra a v1.3.

## Convenciones acordadas durante la discusión

- **Idioma**: español (es-MX) para naming de campos, UI, documentación.
- **Naming preferido**: `ubicacion` (no `columna`); posiblemente `calificador` (en vez de `adjetivo`).
- **Estilo de modelo**: simplicidad > flexibilidad; modelo plano > normalizado profundo; datos visibles > opacos (anti-JSONB cuando no se justifica).
